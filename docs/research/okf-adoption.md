# Research — should lean-flow adopt OKF (Open Knowledge Format) for its knowledge corpus?

> **Question.** Should lean-flow reframe its knowledge corpus (LEARNINGS · ADR · research + ADR-009
> metadata + generated `knowledge-index.md`) as an [OKF](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)-conformant
> *Knowledge Bundle* — for portability/interop — or keep its current stricter, typed, repo-internal model?
> **Verdict.** **Keep the current model; adopt OKF only as an optional *generated export/view*, never the authoring format.** lean-flow already implements ~80% of OKF and its own model is *richer* (typed relations) and *stricter* (enforced lint). OKF is convergent validation, not an upgrade. Its one unmatched value — portability — is a hypothetical need today (YAGNI).

## Why this matters

The corpus is what `/prime`, the loop, and TASK-040's future graph view all read. Adopting OKF as the *authoring* format would migrate every frontmatter block **and** gut the strict `qa-check.sh` lint (OKF mandates permissive consumption). Guessing wrong = a hard-to-reverse format migration that trades away enforcement we deliberately built (L-013).

## Options considered

- **A — Keep current model, ignore OKF.** *Trade-off:* zero cost, keeps typed relations + strict lint; no portability story.
- **B — Optional OKF *export* as a generated derived view (recommended).** *Trade-off:* agent/tool portability *when needed*, additive, down-projects at generation so it never touches authoring; but a second generated artifact to maintain.
- **C — Migrate the corpus to OKF as the authoring format.** *Trade-off:* standard alignment/interop, but loses typed relations, forces permissive (guts the strict lint), high migration cost — hard to reverse.

## Findings

- **lean-flow already implements ~80% of OKF** — markdown + YAML frontmatter, index generated by scanning frontmatter (`gen-index.sh` → `knowledge-index.md`), `tags`, timestamps, IDs, append-only log (CHANGELOG / Execution Log), `index.md`-style listings (TODO · INDEX · DECISIONS), human+agent-readable, no SDK. *Source:* OKF SPEC.md §§2–6 vs the lean-flow corpus.
- **lean-flow is richer on relations.** Ours are *typed* (`related` · `supersedes` · `depends-on`); OKF links are *untyped* + relation-in-prose. Downgrading would lose the transitive supersedes-lineage TASK-040 explicitly wants. → A/B.
- **lean-flow is stricter — and that conflicts with OKF head-on.** `qa-check.sh` *enforces* the tag vocab + metadata completeness (it fails the build — it caught a bad tag this very session); OKF *mandates* permissive consumption (tolerate unknown types, fields, broken links). Adopting OKF-authoring would gut deliberate enforcement (L-013 "convention isn't enforcement"). → reject C.
- **OKF's real unmatched value is portability** — an org/tool-portable bundle (Obsidian/Notion, cross-repo) readable with no SDK. But lean-flow's corpus is consumed *in-repo by its own skills*; portability is a hypothetical, not a current need (YAGNI). → B only if the need becomes real.
- **`type` field + `resource` URI are minor gaps** — directory/template already conveys `type`; `tracker:` covers the task `resource` case. Not worth a migration. → A.
- **Export ≠ authoring.** An OKF view can down-project (typed→untyped, strict→permissive) *at generation time* — the same derived-view/single-SSOT pattern as `knowledge-index.md` and TASK-040's graph. Zero conflict as long as OKF stays a generated **output**, never the source. → B.

## Recommendation

**Keep the current model (A) as the baseline; treat OKF as an optional *generated export* (B) if and when cross-tool/agent portability becomes a real, demonstrated need. Reject format migration (C).** The export down-projects at generation, so it never weakens the typed relations or the strict lint — the exact "derived view, one SSOT" discipline behind TASK-040's graph and the banned-codemap rule. **No ADR now** (the decision is easily-reversible and unsurprising); promote to an ADR **only if** OKF-export is actually built *and* it forces relaxing the lint — that's the genuine hard-to-reverse + trade-off fork.

## Out of scope / open questions

- **The graph VIEW itself (TASK-040)** — OKF-export and the graph are the *same* derived-view shape; sequence them together if either is built. Add an "OKF-export could be the portable sibling of the graph view" note to TASK-040.
- **The strict-vs-permissive philosophical tension** only becomes a live decision if OKF-*authoring* is ever reconsidered — it is rejected here, so the tension stays dormant.
- **No TASK filed for OKF-export** — deferred (YAGNI) until portability is demonstrated; tracked as a note on TASK-040 rather than a standalone backlog item.
